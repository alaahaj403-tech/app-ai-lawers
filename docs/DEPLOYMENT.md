# Deployment

Voxeli ships as two containers (API, web) plus PostgreSQL and Redis. The mobile app talks to the API directly; the web app talks to it through its BFF.

## Images

- `services/api/Dockerfile` — multi-stage; runtime holds only the API's production dependencies, compiled output and `drizzle/` migrations. Runs as a non-root user; `HEALTHCHECK` on `/health`.
- `apps/web/Dockerfile` — Next.js standalone output; `API_URL` and `COOKIE_SECURE` are runtime env, nothing secret is baked in.
- CI builds both images on every push and boots the API image against a throwaway PostgreSQL to prove `/ready` (job `images`). This environment has no Docker daemon, so local image builds are **IMPLEMENTED_NOT_RUNTIME_VERIFIED** until CI runs.

## Release procedure (any platform)

1. **Migrate first, then deploy.** Run `node dist/db/migrate.js` (API image) against the production database as a one-shot job. Migrations are additive SQL files generated by drizzle-kit and reviewed in PRs; never run schema sync in production.
2. Roll the API. `/ready` must return `database: "ok"` and `aiProvider: "openai"` before traffic shifts.
3. Roll the web. Set `API_URL` to the _internal_ API address and `COOKIE_SECURE=true`.
4. Run `scripts/smoke.sh https://api.<domain> https://app.<domain>`. It fails if the mock AI provider is live, if anonymous access is not rejected, or if the BFF accepts cross-site mutations.
5. Rollback = redeploy the previous image tag. Migrations are forward-only; write a new migration to undo a schema change rather than editing an applied one.

## Required production configuration

| Variable                                           | Value                                                                        |
| -------------------------------------------------- | ---------------------------------------------------------------------------- |
| `NODE_ENV`                                         | `production` (enables the strict env checks below)                           |
| `DATABASE_URL`                                     | Postgres URL with TLS (`?sslmode=require`)                                   |
| `REDIS_URL`                                        | required when running more than one API instance (shared rate limits)        |
| `JWT_SECRET`                                       | ≥32 random bytes; rotate with `JWT_PREVIOUS_SECRET`                          |
| `OPENAI_API_KEY`                                   | server-side only; the process refuses `AI_PROVIDER=mock` in production       |
| `EMAIL_PROVIDER` / `RESEND_API_KEY` / `EMAIL_FROM` | `resend` + key + verified sender; `console` is refused in production         |
| `APP_BASE_URL`                                     | `https://app.<domain>` — used in verification and reset links; must be https |
| `CORS_ORIGINS`                                     | the web origin(s) only                                                       |
| `AUTH_RATE_LIMIT_MAX` / `RATE_LIMIT_MAX`           | tune per instance; defaults 10 / 120 per minute                              |

Boot fails fast with the list of violated rules (names only, never values).

## Platform notes

- **Managed containers** (Fly.io, Railway, Render, Cloud Run): one service per image, the platform's secret store for the table above, a release command for the migration step, and a managed Postgres with automated backups. Redis is required once you scale the API past one instance.
- **Single VM**: `infrastructure/docker-compose.prod.yml` is the reference topology (API, migrate job, web, Postgres, Redis). Put a TLS-terminating reverse proxy in front and keep 5432/6379 off the public interface.
- **Web on Vercel**: possible (Next.js standalone is not needed there); set `API_URL` and `COOKIE_SECURE=true` as server env vars. The BFF's same-origin check uses the request `Host`, so custom domains work without configuration.

## Backups and recovery

- Daily automated Postgres snapshots + WAL/PITR where the provider offers it. **A backup is not done until a restore has been rehearsed**: restore the latest snapshot to a scratch database and run `scripts/smoke.sh` against an API pointed at it, at least before launch and after every major schema change.
- Object storage is not used yet (audio is never stored), so the database is the only stateful component besides Redis, which is a cache and may be lost without data loss.

## Observability

Pino JSON logs to stdout with redaction of auth headers, passwords, refresh tokens and translation text; `x-correlation-id` on every response and propagated to providers and `ai_usage`. Ship stdout to the platform's log drain. Alert on: `/ready` failing, 5xx rate, `ai_usage.success = false` rate per provider, and `realtime_sessions.metrics.closeReason = 'provider_unavailable'`.
